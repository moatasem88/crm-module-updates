Part 02

The setup layer — customizations created by code

No Custom Field or Property Setter in this project was created by hand. Three functions build all of them, and after_migrate runs those functions on every deployment of every site.

The pattern

custom_crm_updates/overrides/opportunity.pyPythonafter_migrate
def apply_opportunity_customizations():
    from frappe.custom.doctype.custom_field.custom_field import create_custom_fields
    from frappe.custom.doctype.property_setter.property_setter import make_property_setter

    create_custom_fields(CUSTOM_FIELDS, update=True)

    # Extend core's options (read from the DocField, not the merged meta) so
    # options ERPNext adds later are kept.
    options = frappe.db.get_value(
        "DocField", {"parent": "Opportunity", "fieldname": "status"}, "options"
    ).split("\n")
    options += [status for status in EXTRA_STATUSES if status not in options]
    make_property_setter(
        "Opportunity", "status", "options", "\n".join(options), "Text",
        validate_fields_for_doctype=False,
    )

    for fieldname in HIDDEN_FIELDS:
        make_property_setter(
            "Opportunity", fieldname, "hidden", 1, "Check", validate_fields_for_doctype=False
        )
Idempotence
create_custom_fields(..., update=True) inserts a missing field and updates an existing one. make_property_setter deletes any existing setter for the same doctype/field/property before inserting, so re-running replaces rather than duplicates.
Upgrade safety
The status options are rebuilt from the original DocField row, not from frappe.get_meta() (which already includes our setter). Reading the merged meta would append our two options to a list that already contains them — harmless here because of the not in guard, but it would also silently freeze whatever ERPNext shipped at that moment. Reading DocField means a status ERPNext adds in v15 survives.
Failure isolation
validate_fields_for_doctype=False stops a setter for a field that no longer exists from aborting the entire migrate.
Cleanup
OBSOLETE_CUSTOM_FIELDS in lead.py deletes fields from earlier iterations (an HTML field replaced by the activities table). Removing a dict from CUSTOM_FIELDS does not delete the field from the database — you must delete it explicitly.

Reordering core fields: the field_order rebuild

def apply_field_order():
    """Standard fields can only be reordered through a `field_order` Property
    Setter (what Customize Form saves), so rebuild it from the current order
    with our moves applied. Other reorderings made through Customize Form are
    preserved."""
    fields = frappe.get_meta("Lead", cached=False).fields
    order = [df.fieldname for df in fields]
    fieldtypes = {df.fieldname: df.fieldtype for df in fields}

    new_order = move_section(order, fieldtypes, "organization_section", before="contact_info_tab")
    # A Tab Break takes every field up to the next one, so the address section
    # has to sit right before Activities rather than mid-Details.
    new_order = move_section(
        new_order, fieldtypes, "address_section", before="activities_tab", header=ADDRESS_TAB
    )
    new_order = move_section(new_order, fieldtypes, CONTACT_SECTION, before="activities_tab")

    if new_order == order:
        return

    frappe.make_property_setter({...  "property": "field_order",
                                      "value": json.dumps(new_order)},
                                validate_fields_for_doctype=False)
  • Read, transform, write — never a hard-coded list. A field ERPNext adds later appears in order and is carried through; a manual reordering by an administrator is preserved unless it conflicts with one of the three moves.
  • cached=False matters. During migrate the cached meta can predate the Custom Fields that were created moments earlier in the same function.
  • No-op guard. If the computed order equals the current one, no Property Setter is written — so a repeated migrate produces no document churn.
  • Section-aware moves. move_section takes the section break and every field up to the next break, which is the only correct way to move a block in Frappe's flat field list.

Where a Custom Field actually lands on the form

Two different mechanisms, and confusing them is a real trap:

idx
Computed only when the Custom Field row is created (CustomField.validate runs the lookup under if self.is_new() or self.insert_after == "append"). Changing insert_after on an existing field does not recompute it.
insert_after
What Meta.sort_fields() actually uses at meta-build time: it collects custom fields into an insert_after_map and splices each one in after its anchor. So editing insert_after does move the field on the form, even though idx is stale.
Consequence
Order the dicts in CUSTOM_FIELDS so each anchor already exists when the next field is created (the tab before its table, the table before the field that follows it). custom_approved_project_tender is declared after custom_project_tenders and anchored to it, which is why it renders directly below the table.
Part 03

Mechanism: populating a child table safely

Four tables on this project show records that live in another DocType: the Lead's activities, the Opportunity's activities, the Opportunity's Project Tenders, and the Contacts tables on both. All four are written by the same 33 lines. This section is the full reasoning behind those lines.

The problem

A Frappe child table is not a view. Its rows are real records in the child DocType's own table, keyed by parent, parenttype and parentfield. To show Leads Activity records inside the Lead's form as a grid, those rows have to be physically written into tabLeads Activity Detail against that Lead — and rewritten whenever the source changes. The naive implementations all fail:

Naive approachWhy it fails here
parent_doc.save() after changing the rowsRuns the parent's full validation and all its hooks. A Lead with an unrelated validation problem would block an activity save; ERPNext's own Lead/Opportunity validations would run on a document the user never touched; and our own validate hooks would re-enter, risking recursion.
An HTML field rendering a server-side listNo grid: no ⚙ column picker, no sorting, no export, no per-user column widths. This was the first implementation and was replaced (its leftover field is in OBSOLETE_CUSTOM_FIELDS).
Raw frappe.db.sql insertsBypasses child-row naming, idx maintenance and the document cache; the open form would then show rows the cache does not know about.
Writing on read (onload)A read request that writes is a lock and replication hazard, and it cannot help the list view or a report.

The implementation

custom_crm_updates/mirror_table.py — all 33 linesPython
import frappe
from frappe.utils import now


def rows_differ(existing, rows, fields):
    """Compare as strings so a date loaded from the DB equals one from a query."""

    def normalize(row):
        return [None if row.get(f) is None else str(row.get(f)) for f in fields]

    return [normalize(r) for r in existing] != [normalize(r) for r in rows]


def set_mirror_rows(doctype, name, fieldname, rows, fields, bump_modified=True):
    """Write `rows` into `name`'s `fieldname` table directly, without a full
    save (no validations or hooks of the parent run). No-op when unchanged.

    bump_modified: makes a stale open form refuse to save (and so overwrite
    these rows) and reloads it instead. Tables that the parent recomputes on
    its own save don't need it."""
    doc = frappe.get_doc(doctype, name)
    if not rows_differ(doc.get(fieldname), rows, fields):
        return False

    doc.set(fieldname, rows)
    doc.update_child_table(fieldname)
    if bump_modified:
        doc.db_set("modified", now(), update_modified=False, notify=True)
    return True

Four decisions are encoded here. Each one is load-bearing.

Decision 1 · update_child_table instead of save()

Document.update_child_table(fieldname) is a Frappe API that writes only that table: it inserts or updates the rows now in memory and deletes the child rows of that parentfield that are no longer present. The parent row itself is not written, no validate runs, no on_update fires, no Version/audit entry is created for the parent.

  • No permission check, by design. The user saving a Leads Activity may have no write access to the Lead. The mirror row is derived data about a record they can already read, so the write is a system action, not the user's.
  • No recursion. Because the parent's on_update does not fire, a Contact that touches an Opportunity cannot trigger a chain back into the Contact.
  • Child rows are still real documents. They get proper names and idx values, so the grid, exports and reports behave normally.
The trade-off is explicit: the parent's modified_by and its Version history do not record these row changes. That is acceptable because each mirror row carries a Link to the record it mirrors, and that record has its own full audit trail.

Decision 2 · compare before writing (rows_differ)

Every sync first rebuilds the desired rows, then compares them field-by-field with what is stored. If they match, the function returns False and touches nothing.

Why string-normalise
A date loaded from the database is a datetime.date; the same value from frappe.get_all may be a string, and a Currency may be Decimal vs float. Comparing str(...) of each field in a fixed order makes the comparison stable, so a no-change sync is reliably detected as no change.
Why it matters
Without it, every save of every activity would rewrite rows and bump the parent's modified, which (a) makes every open Lead form reload constantly, (b) produces write amplification on a hot record, and (c) destroys the usefulness of modified as a change signal.
Where it pays off
after_migrate runs three backfills over every record that has activities, tenders or contacts. On an unchanged site that whole pass performs zero writes — and there is a test asserting the parent's modified is identical after a second backfill.
Fixed field tuples
DETAIL_FIELDS, TENDER_ROW_FIELDS, CONTACT_ROW_FIELDS define which columns participate. A column added to the child DocType but not to the tuple will never be detected as changed — see Risks.

Decision 3 · bumping modified is the concurrency control

This is the subtlest part of the design, and the reason the tables cannot silently lose data.

doc.db_set("modified", now(), update_modified=False, notify=True)

Frappe uses the modified timestamp for optimistic concurrency: on every save it compares the timestamp the client sent with the one in the database and raises TimestampMismatchError ("Document has been modified after you have opened it") if they differ. Consider the race this prevents:

  1. User A opens Lead L. Their browser now holds a copy of L including its current mirror rows.
  2. User B logs a new activity against L. The sync writes a new mirror row into L.
  3. User A, still on the stale form, edits a phone number and saves. The browser posts its whole document, including the old child rows — which would delete B's new row.

Because step 2 bumped modified, step 3 is refused and the form reloads instead. The row survives. notify=True publishes a realtime doc_update event, so a form that is open and not dirty reloads immediately rather than waiting for the user to hit save and get an error. update_modified=False prevents Frappe from overwriting the explicit timestamp with its own.

Tested

test_sync_invalidates_stale_lead_form holds a stale copy of the Lead, creates an activity, and asserts that saving the stale copy raises frappe.TimestampMismatchError. If someone "optimises" the bump away, that test fails.

Decision 4 · when not to bump — the Contacts table

The contacts mirror passes bump_modified=False, and that is not an inconsistency. It is maintained from three directions:

DirectionHookWrite path
The parent saves itselfLead / Opportunity validate → refresh_own_tableSets the rows in memory on the document being saved, so they are written by that save.
A Contact changesContact on_update / on_trashsync_contact_table → set_mirror_rows(..., bump_modified=False). affected_docs adds the Lead behind each linked Opportunity.
An Opportunity appears, moves or goesOpportunity on_update / on_trashrefresh_party_lead → the Lead's table. No Contact changed, so no Contact event would fire; the roll-up still has to follow.

Because the parent recomputes this table from scratch on its own save, a stale form cannot leave wrong rows behind: whatever rows it posts are immediately overwritten by the recomputation during validate. The optimistic-lock protection is therefore unnecessary here, and skipping it avoids reloading every open Lead form whenever anyone edits an unrelated contact.

The activities and tenders tables cannot use that trick: a Lead's validate does not know about Leads Activity, and recomputing a tender list on every Opportunity save would couple the Opportunity to the contracting app. Hence they bump; contacts do not.

Concurrency analysis

Transaction boundary
One HTTP request (or one background job) is one MariaDB transaction in Frappe. A sync therefore commits atomically with whatever triggered it: if the activity save fails later, its mirror write is rolled back too — the table can never show a row for a record that does not exist.
Two concurrent syncs
Each sync recomputes the full row set from the source of truth rather than applying a delta. Two activities saved at the same instant produce two full recomputes; whichever commits last writes a complete, correct set. Last-writer-wins is safe precisely because nobody writes a partial update.
The interleaving window
A sync reads the source, compares, then writes. If another transaction inserts a source record between the read and the write, the row set written can be one record behind — but that other transaction runs its own sync immediately after, which brings the table level. Convergence is guaranteed by the fact that every writer recomputes everything.
Locking
frappe.get_doc does not lock. db_set on the parent takes a row lock on that single parent row for the rest of the transaction. Two syncs of the same parent serialise there; syncs of different parents never contend. Lock ordering is consistent (child rows then parent row), so this pattern does not deadlock against itself.
Deletes
on_trash handlers pass exclude=<name> and run before Frappe's link-existence check. The mirror row holds a Link to the record being deleted, which would otherwise raise LinkExistsError and make the record undeletable. Removing the row first is what keeps delete working.
Background jobs
Nothing here is queued — all syncs run inline in the triggering request. That keeps them inside the same transaction (no "row appears five seconds later" window) at the cost of a little latency on save. For much larger row sets, moving to frappe.enqueue would require giving up that atomicity deliberately.

Mechanism: writing to the document that is currently saving

The approved-tender flow (modification 2) breaks the assumption every other sync relies on: the parent being updated is the document in the middle of its own save. This needed two extra pieces.

Frappe's save lifecycle, and where the hooks sit

The failure this avoids

Without the two extra pieces, the Won flow would do this:

  1. The Opportunity's row is written, modified = T1. The in-memory document (the one that will be returned) holds T1.
  2. on_update saves the Project Tender as Won.
  3. The tender's own on_update calls sync_opportunity_tenders, which bumps the Opportunity's modified to T2 in the database.
  4. The response hands the browser a document claiming modified = T1, while the database says T2 — so the user's next save is rejected with "Document has been modified", on a document only they were editing.

The realtime notify would often paper over it by reloading the form, but that is a race, not a fix.

The fix: a suppression flag plus an in-memory refresh

def set_tender_won(tender_name, opportunity):
    tender = frappe.get_doc("Project Tender", tender_name)

    tender.status = "Won"
    tender.flags.ignore_permissions = True
    # The Opportunity is mid-save; apply_approved_tender refreshes its table.
    tender.flags.skip_opportunity_sync = True
    tender.save()
    ...
    return True


def on_update(doc, method=None):
    """doc_events: Project Tender on_update (after contracting's own)."""
    before = doc.get_doc_before_save()
    # skip_opportunity_sync: saved from apply_approved_tender, i.e. from the
    # Opportunity's own save, which refreshes its table itself (see there).
    if not doc.flags.get("skip_opportunity_sync"):
        for opportunity in {doc.get(OPPORTUNITY_FIELD), before and before.get(OPPORTUNITY_FIELD)} - {None}:

    ...


def refresh_tender_rows(doc):
    """The table of an Opportunity that is being saved right now: written
    through the document itself, and without the modified bump
    sync_opportunity_tenders makes — the form doing the saving would otherwise
    come back one step behind the database and refuse its next save."""
    rows = tender_rows(doc.name)
    if rows_differ(doc.get(TENDER_TABLE), rows, TENDER_ROW_FIELDS):

        doc.update_child_table(TENDER_TABLE)
doc.flags
A per-document scratch dict that is not persisted. It travels with the in-memory object through the save, so a hook can tell "who saved me". This is the idiomatic Frappe way to pass intent down a call chain without a global.
Why not a module global
A global would leak across documents in the same request and across jobs in the same worker process. Document flags are scoped to the object.
Net effect
The tender is saved (its own Won automation runs in full), the usual bump is suppressed for this one path, and the Opportunity's rows are rewritten through the saving document — so database and response agree, and modified is untouched.
Verified
test_the_saved_form_is_not_left_behind_the_database asserts opportunity.modified equals the database's value after the Won save.

Rollback semantics — a deliberate choice

set_tender_won performs a full tender.save(), so the contracting app's own Won automation runs: it raises a Project and a Sales Order per linked Tender, and its validate_won_preconditions can refuse (a Tender that is not Complete, a BOQ row with no Item, a non-integer quantity on a whole-number UOM).

That exception is allowed to propagate. It aborts the request, so the Opportunity's own save is rolled back with it. The alternative — catching it — would leave a Won Opportunity whose approved tender is not Won and whose Project was never created. A loud failure with contracting's own precise message was judged better than a quiet split-brain.

Trade-off

The cost is that a user cannot close the Opportunity as Won until the tender is genuinely ready. That is a business rule inherited from the contracting app, not one this app invented — but it is worth knowing before someone reports it as a bug.

Mechanism: a document that joins another document's table when it is inserted

A Tender names a Project Tender (Tender.project_tender, mandatory). Since 14 October that is also what costs it in: on insert, the Tender adds its own row to the Project Tender's Direct Cost Details, whether it came from Create ▸ Tender or was raised on the Tender form with the Project Tender picked by hand. Three framework details decide how this is written.

Where it hooks, and why not on_update

Document.insert() runs after_insert before run_post_save_methods() calls on_update. That ordering is load-bearing: the Tender's own on_update runs the cross-sync, which looks for Direct Cost rows referencing this Tender. Adding the row in after_insert means the sync finds it on the same save and pushes the Tender's cost into it immediately; an on_update hook would race with it.

Re-entrancy: never save the document you are inside

Saving the Project Tender fires its on_update, which pushes propagated_addition_percent down to every linked Tender — including the one still being inserted. That second save writes a new modified for a row whose in-memory copy is about to be returned to the browser, and the user's next save is rejected as stale. The fix is the flag the contracting app already uses for its own loop:

project_tender.append("direct_cost_details", {"tender": tender_doc.name})
project_tender.flags.skip_cross_sync = True      # ← do not push back into me
project_tender.save(ignore_permissions=True)

Nothing is lost by suppressing it: the Tender's own on_update, a few lines later, runs the full pass with skip_tender=tender_doc.name, which pushes to every other Tender and deliberately skips this one.

Mechanism: recording the date a status was reached

Six fields across four DocTypes record when something happened: Lead.date_of_convert, Tender.completion_date, Project Tender.submitted_date and won_date, Opportunity.won_date, and the mirrored completion_date column on Project Tender Direct Cost Detail. All five writable ones use one shape, and each clause in it answers a specific failure.

def set_completion_date(doc, method=None):
    if doc.get(COMPLETION_DATE) or doc.status != COMPLETE:   # 1. already recorded / wrong status
        return
    if doc.has_value_changed("status"):                      # 2. this save actually moved it
        doc.set(COMPLETION_DATE, nowdate())                  # 3. in validate, not on_update
1 · the empty check
has_value_changed alone is not enough. A record that goes Converted → Open → Converted changes its status twice and would be re-stamped with the second date; the rule is "when did this first happen", so a field that already holds a date is never written again.
2 · has_value_changed
Without it, every ordinary re-save of a record already in that status would re-stamp it. It compares against get_doc_before_save() and returns True for a new document, so a record created directly in the target status is stamped too.
3 · validate, not on_update
In validate the date is part of the same UPDATE as the status it describes: there is no instant at which a tender is Submitted with no Submitted Date, and no second write to roll back separately. For Tender it is the only option — see below.

Why a locked DocType forces the hook into validate

Contracting locks a Tender the moment it is Complete: validate_not_complete_locked compares self.as_dict() with get_doc_before_save().as_dict() and throws on any difference. A date written after the status change would therefore be refused for ever. It works because Frappe composes the controller method and the hooks in that order — frappe/model/document.py's hook decorator runs fn(self) first, then each doc_events handler — so by the time our validate hook writes the field, the lock check has already run and passed against the old status.

The one write that no document hook can see

Lead.date_of_convert needs a second entry point. ERPNext marks a Lead Converted from the Customer side:

# erpnext/selling/doctype/customer/customer.py
def update_lead_status(self):
    if self.lead_name:
        frappe.db.set_value("Lead", self.lead_name, "status", "Converted")

That is a direct UPDATE. No Lead document is loaded, so no validate, no on_update, no doc_events of any kind fire on the Lead — the usual route to Converted, through a Registration activity, would stamp nothing. The second handler therefore hangs off Customer on_update, re-reads the Lead's status from the database to confirm the conversion, and writes the date the same way, with update_modified=False. The lesson generalises: before hooking a status, grep for db.set_value and db_set on that field — a framework that lets code bypass the document layer will have done so somewhere.

Mirroring a date onto a child row without a sync function

The Completion Date column on Direct Cost Details is not a mirror table: it is a Custom Field with fetch_from: "tender.completion_date". Frappe re-resolves every fetch_from on each save of the parent (base_document.py, in the link-validation pass), and contracting's sync_tender_to_project_tenders already saves every linked Project Tender whenever a Tender is saved — so the column follows with no code at all. push_completion_date_to_rows writes the same value directly onto the rows as well, the way cross_sync writes tender_total, for the paths where that parent save is skipped.

Backfills differ by what evidence exists. A Lead's conversion date comes from its Customer's creation; Leads marked Converted by hand with no Customer stay blank rather than being given the migrate's date. A Tender's comes from modified, which is sound because Complete locks the record — nothing has been able to save it since. Project Tender and Opportunity get no backfill: both are re-saved routinely, so modified would be a guess, and a wrong date is worse than an empty field.

Part 06

Multi-site behaviour and cross-site concurrency

This bench serves two sites from one copy of the code. Understanding what is shared and what is not is the difference between a deployment that works and one that half-works.

Correct a common assumption

There is no synchronization between sites, and there must not be. A mirror table on site1.local is rebuilt only from records in site1.local's own database. The word "concurrent" across sites means two independent request streams running the same code against different databases — never one site observing the other. If cross-site data sharing is ever required, it has to be built explicitly (an API call, a sync job), and none of the mechanisms in this document provide it.

Injection and output-escaping surface

SQL
Every query goes through frappe.get_all / frappe.db.get_value with dict or list filters, which are parameterised. There is no frappe.db.sql anywhere in the app.
f-strings in queries
Two exist — f"{ACTIVITY_FIELD} as leads_activity" and the order_by strings. Both interpolate module-level constants, never user input. Keep it that way: a fieldname or order_by built from a request parameter is an injection vector, because those parts cannot be parameterised.
Child-table filters
get_contact_rows uses the list form [["Dynamic Link", "link_doctype", "=", doctype], ...], which Frappe compiles to a join with bound values. The order_by is table-qualified (`tabContact`.creation) because the joined table also has a creation column — a correctness fix, not a security one.
HTML in messages
frappe.msgprint and add_comment render HTML. The only interpolated values are system-generated record names and get_link_to_form output. If you ever interpolate a user-entered field (a project name, a person's name) into a message, escape it — frappe.utils.escape_html — or you have stored XSS in the timeline.
Client-side
The popup builds Select options from server data and assigns them as option values/labels, not as HTML. The one HTML field in the dialog is a static string. The pre-existing project_tender.js grid formatter already uses frappe.utils.escape_html for the same reason.
Translations
Messages are Arabic source strings inside _(). Nothing security-relevant, but worth noting: _() resolves against the user's language, so a translation file can change what a user sees without a code change.

def contact_sources(doctype, name, exclude_opportunity=None):
    """The documents whose contacts this table lists. An Opportunity lists its
    own; a Lead lists its own first, then those of each Opportunity made from
    it, oldest Opportunity first.

    exclude_opportunity: an Opportunity being deleted. It is still in the
    database while on_trash runs, so it has to be left out by hand."""
    sources = [(doctype, name)]
    if doctype != "Lead":
        return sources

    sources += [
        ("Opportunity", opportunity)
        for opportunity in frappe.get_all(
            "Opportunity",
            filters={"opportunity_from": "Lead", "party_name": name},
            pluck="name", order_by="creation asc",
        )
        if opportunity != exclude_opportunity
    ]
    return sources


def refresh_party_lead(doc, method=None):
    """doc_events Opportunity on_update / on_trash: a Lead rolls up the
    contacts of its Opportunities, so it has to follow an Opportunity being
    created, re-pointed at another Lead, or deleted."""
    before = doc.get_doc_before_save()
    leads = {lead_of(doc.name)} if method != "on_trash" else set()
    if before and before.opportunity_from == "Lead":
        leads.add(before.party_name)
    if method == "on_trash" and doc.opportunity_from == "Lead":
        leads.add(doc.party_name)

    for lead in leads - {None}:
        sync_contact_table(
            "Lead", lead, exclude_opportunity=doc.name if method == "on_trash" else None
        )
Asymmetry in one place
A single function decides direction for both tables: an Opportunity returns one source, a Lead returns itself plus its Opportunities. Nothing else in the sync path changed.
De-duplication
get_contact_rows keeps a seen set across sources, so a contact linked to both the Lead and one of its Opportunities appears once, attributed to the first source that has it.
The on_trash subtlety
Frappe runs on_trash before the row is gone, so the Opportunity being deleted is still returned by the sources query. exclude_opportunity removes it — the same trick the other mirrors use with exclude.
In practice
Frappe refuses an ordinary delete of an Opportunity that a Contact links to (LinkExistsError), so this path matters for a forced delete and for Opportunities with no contacts. The test reaches it with force=True.
Why a separate hook
Linking a contact fires a Contact event, which affected_docs already routes to the Lead. An Opportunity being created, re-pointed or deleted changes the roll-up with no contact involved, so it needs its own trigger.

Part 09

Risks and pitfalls when repeating these solutions

Each item is a real failure mode of the patterns in this document — several were hit during development.

1 · Bumping modified on the document that is currently saving

A sync triggered from inside a document's own on_update writes a new modified to the database while the in-memory document returned to the client still holds the old one. The user's next save is then rejected on a document only they were editing.

Mitigation: suppress the sync for that path (doc.flags.skip_opportunity_sync) and refresh the rows through the saving document instead (refresh_tender_rows). Pin it with a test that compares doc.modified to the database value.

2 · Removing the modified bump as an "optimisation"

It looks like pointless write traffic. It is the optimistic lock that stops a stale open form from posting its old child rows over newly synced ones — a silent data loss, invisible in logs.

Mitigation: only drop the bump when the parent recomputes that table during its own validate (as the contacts table does). Otherwise keep it.

3 · Adding a column to a mirror child DocType and forgetting the compare tuple

rows_differ only inspects the fields listed in DETAIL_FIELDS / TENDER_ROW_FIELDS / CONTACT_ROW_FIELDS. A new column that is populated by the query but missing from the tuple will never register as a change, so existing rows keep a stale value forever.

Mitigation: three edits always go together — the child DocType JSON, the sync query, and the …_FIELDS tuple.

4 · An automation without an "already done?" question

on_update fires on every save. Without has_value_changed("status") or an existence check, the Tendering automation would create a tender per save and the Won automation would re-run its Project/Sales Order creation.

Mitigation: idempotence by database question (frappe.db.exists("Project Tender", {ACTIVITY_FIELD: ...})) plus a change guard. Test the double-save explicitly — test_resaving_activity_does_not_create_another does.

5 · Child-table mirror rows blocking deletion

A mirror row holds a Link to the record it mirrors, so deleting that record raises LinkExistsError and the record becomes undeletable.

Mitigation: an on_trash handler that re-syncs with exclude=<name>. It must run before Frappe's link check, which doc_events on_trash does.

6 · Changing what a mirror shows without changing what writes to it

Modification 6 narrowed the Opportunity's contact query. Had the New Contact button not been changed too, it would have kept linking new contacts to the Lead (core leaves frappe.dynamic_link pointing at the party) — the contact would vanish from the table the user created it in, with no error anywhere.

Mitigation: when a read changes, enumerate every writer: buttons, link-field queries, mappers, imports.

7 · Trusting mandatory_depends_on or read_only as a rule

In Frappe v14 mandatory_depends_on is evaluated on the form only. read_only is bypassed by whitelisted methods, Data Import and anything with ignore_permissions. Either one alone is a suggestion, not an invariant.

Mitigation: pair every one of them with a server validate. This app does so three times.

8 · reqd on a DocType that the framework also creates

ERPNext inserts Leads itself from the website contact form, from incoming email and from appointments. Marking a field reqd breaks all of those paths with no user present to fix it.

Mitigation: mandatory_depends_on: "eval:1" for the form plus a server check that exempts flags.ignore_permissions / flags.ignore_mandatory inserts — and complete those records before the data is needed (convert_lead_to_customer asks at the point of use).

9 · Hard-coding a Select's options in a Property Setter

Writing the full option list as a literal silently deletes any option a future ERPNext release adds.

Mitigation: read the original list from the DocField row (not the merged meta), append what is missing, write that back.

10 · Assuming insert_after re-sorts an existing Custom Field

idx is computed only when the Custom Field is created. Editing insert_after later leaves idx stale — the form order does follow insert_after (via Meta.sort_fields), but two fields anchored to the same field with equal idx can order unpredictably.

Mitigation: anchor each new field to the previous one in the chain, and declare them in that order in CUSTOM_FIELDS.

11 · Letting a nested save's exception leave a split state — or swallowing it

The Won flow saves another app's document inside on_update. If that save raises and the exception is caught, you get a Won Opportunity whose approved tender is not Won. If it propagates, the whole request rolls back.

Mitigation: decide explicitly and write the decision down. Here propagation was chosen; the comment in set_tender_won says why.

12 · Forgetting that each site is a separate database

New code reaches every site immediately; new fields do not. A site that was not migrated runs the new hooks against a schema that lacks the new field, and the feature fails quietly (doc.get(...) is simply None).

Mitigation: migrate and clear-cache every site in the deployment script, not just the current one. Guard cross-app code with frappe.db.exists("DocType", ...).

13 · Interpolating user text into msgprint or add_comment

Both render HTML. Today only system-generated names and get_link_to_form output are interpolated, so there is no issue — but a project name or a person's name dropped into the same string is stored XSS in the timeline.

Mitigation: frappe.utils.escape_html on anything a user typed, server and client alike.

14 · Writing Arabic (or any localised) text as the source string without _()

The text then cannot be overridden per site or per user, and a bilingual site is stuck with one language.

Mitigation: keep the string inside _() even when it is already in the target language, as this app does. Remember that _() resolves against the user's language — which is exactly why a translations/ar.csv would not have worked here: every user on this bench is set to en.

15 · Assuming frappe.copy_doc respects no_copy

It does the opposite by default: the signature is copy_doc(doc, ignore_no_copy=True), and its docstring is the single line "No_copy fields also get copied." A one-shot marker field carried into a clone silently re-runs whatever it marks. Here, a Tender raised from a Project Tender used to carry a flag; create_revised_version clones with copy_doc, so every revision arrived with the flag set and would have added a second Direct Cost row for the same scope — double-counting the price.

Mitigation: never rely on no_copy to stop a clone; gate on something the clone genuinely differs by (previous_tender is set on a revision and on nothing else). Pin it with a test that clones and asserts the automation did not run.

16 · An automation that collides with the manual step it replaces

Making a child join its parent's table automatically breaks every flow that still adds that row by hand — the parent's own duplicate guard then throws on save. Ten existing tests in the contracting app did exactly that, and so would any user with the old habit.

Mitigation: when automating a step, find every existing caller of the manual version first (grep for the append() and decide per site whether it is now redundant or still needed — one of those ten was kept, because its Project Tender is already Won by then and the automation deliberately skips those.

17 · Throwing from after_insert

The exception propagates out of insert() and rolls the whole document back. An automation that writes to another document from after_insert therefore inherits that document's validation: if the parent refuses the write, the child the user was creating disappears with it, and the error names the wrong document.

Mitigation: check the parent's preconditions before writing and degrade to a message instead of an exception. Here a Tender only joins a Project Tender that is still Draft or Under Review; on a Submitted or Won one the status gate would refuse the row, so the Tender is saved and the user is told the row was skipped.

18 · Comparing a document's modified with one read back from the database

doc.modified is a string; frappe.db.get_value(..., "modified") is a datetime. != is therefore always true, and a staleness check written that way reports a bug that isn't there — as one of this project's own checks did, including for a control case that touched none of the new code.

Mitigation: compare as strings, which is what mirror_table.rows_differ already does for exactly this reason. When a check fails, run it against a case the change cannot have affected before believing it.

19 · Hooking a status that the framework also writes with db.set_value

A doc_events handler only runs when a document is saved. ERPNext marks a Lead Converted with frappe.db.set_value from Customer.update_lead_status — a direct UPDATE that loads no Lead, so no Lead hook of any kind fires. A Date-of-Convert hook on the Lead alone would have been correct, tested, and silently wrong for the most common route into that status.

Mitigation: before hooking a status transition, grep -rn 'db.set_value\|db_set' for that field across the installed apps, and add a handler on whichever document is saved on that path. Test the indirect route, not just the direct one: here test_set_when_a_customer_is_raised_from_the_lead is the test that would have caught it.

20 · Reaching for fetch_from where a value must stay editable

fetch_from is re-resolved on every save of the document, not only on insert. Used as a "default from a related record" it quietly overwrites whatever the user typed, every time they save — and the bug looks like the form losing their input at random. It is a continuous relationship, not a default.

Mitigation: a value the user may change afterwards is filled imperatively in before_insert, into an empty field only. Keep fetch_from for genuinely derived, read-only columns — which is exactly what the Completion Date column on Direct Cost Details is.

21 · Adding a field to a DocType that locks itself

Contracting refuses any edit of a Complete Tender by diffing the document against its pre-save copy. Writing the completion date in on_update, or in a later save, would be refused for ever — and the first sign of it is an exception on a status change that used to work.

Mitigation: write the value in validate, where it joins the same UPDATE as the status. Frappe composes the controller's own method before the doc_events handlers, so the lock check runs against the previous state and the new field rides along with the transition it describes.
