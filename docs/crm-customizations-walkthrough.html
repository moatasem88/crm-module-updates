Every change made to the ERPNext CRM module in this project, in the order it happened — what was done, where it was done, and why. Written for someone who has used ERPNext but has never customized it, so each step also explains the tool it used and when you would reach for that tool yourself.

Part 00

Where to start

Three things to understand before the first step, so the rest reads as a story rather than a list.

1 · Nothing in ERPNext itself was edited

Every change lives in a separate app, custom_crm_updates. ERPNext's own files are untouched, so bench update can upgrade ERPNext without overwriting any of this work. This is the single most important rule in Frappe customization: you add an app beside ERPNext, you never edit inside it.

2 · A DocType is the unit of everything

A DocType is a table, a form and a Python class at once. Lead, Opportunity and Contact are ERPNext DocTypes. Customizing the CRM means adding fields to them, reacting to their save events, and creating new DocTypes of your own (this project created five).

3 · Layout and fields are created by code, not by clicking

You can add a field through the Desk UI (Customize Form). This project does it in Python instead, in functions that run on every bench migrate. The reason is repeatability: the same fields appear on a new site, a test site and a colleague's laptop with one command, and the definitions live in git where they can be reviewed.

Assumptions

Stated once, here, and they hold for both documents. (a) The chronology comes from this app's git history (two commits, 7 Oct 2026) and from the step order recorded in the project's own code guide; the work inside the first commit was reconstructed from that order, so "step 4 came before step 5" is reliable while exact timestamps within a day are not. (b) Project Tender belongs to a separate in-house app, contracting; it is treated here as a third-party DocType that must not be edited, which is how the code treats it. (c) Where a reason was not written down, it is inferred from the code and named as an inference in the text. (d) Field counts, Property Setter counts and test counts were read from the live site1.local database and the current source, not estimated.

Part 01

The five tools — and when to use which

Frappe gives you five ways to change behaviour without editing ERPNext. Every step in this document is one of them. Learn to pick between them and customization stops feeling like guesswork.

ToolWhat it changesLives inReach for it when…
Custom FieldAdds a field to an existing DocTypeThe site's database (created here by Python)You need to store something ERPNext has no field for.
Property SetterOverrides one property of an existing field (hidden, reqd, options, label, field order)The site's database (created here by Python)The field exists but must behave differently — hidden, mandatory, extra Select options, moved.
Hook (doc_events)Runs your Python when a document is validated or savedhooks.py in your appSaving document A must check something or change document B.
Client ScriptRuns your JavaScript in the formA .js file in your app, wired by doctype_jsThe user needs feedback, a button, a popup or a filtered link list.
New DocTypeAdds your own table, form and controllerYour app's module folderThe data you need is a record in its own right, not a field on someone else's.
Watch out

A Client Script is never a rule — it is a convenience. Anything that must always be true needs a Python hook as well, because the REST API, Data Import and the bench console do not run JavaScript. You will see this pair appear twice in Phase 2: the attachment rule and the approved-tender rule each have a form half and a server half.

Part 03 · Phase 1

Building the foundation — steps 1 to 17

In the order they were built. Each card answers the same three questions, then draws out the transferable lesson. 6–7 Oct 2026

01

"Is Company" hides the person fields

A Lead that is a company has no first name, so those fields disappear and are emptied on save.

What

A new Is Company checkbox. When ticked, Salutation, First/Middle/Last Name, Gender and Job Title vanish from the form, and Organization Name becomes the mandatory one instead. On save the hidden values are cleared and Full Name is set to the company name.

Where

DocType Lead. One Custom Field (custom_is_company), six depends_on Property Setters, two mandatory_depends_on Property Setters, and a before_validate hook — all in overrides/lead.py.

Why

Company leads were being saved with a person's name invented to satisfy the mandatory First Name, which polluted reporting. Hiding is not enough on its own: a field hidden after someone typed in it keeps its value, so the values must also be cleared server-side.

Custom FieldProperty SetterHook: before_validate
Lesson. depends_on is a tiny JavaScript expression the form evaluates live — eval: !doc.custom_is_company. It controls visibility only. Pair it with a server hook whenever the hidden data must actually go away. And prefer before_validate over validate when your change must happen before ERPNext's own validation reads the field.
02

The Organization section moved above Contact Info

Sales staff fill in the company first, so the form now follows that order.

What

The whole Organization block (not just its heading) was moved up the Lead form.

Where

DocType Lead, one field_order Property Setter generated by apply_field_order() in overrides/lead.py.

Why

ERPNext's own fields cannot be moved with insert_after — that only works for fields you added. The only supported way is a field_order Property Setter: the complete list of fieldnames in display order, which is exactly what Customize Form writes when you drag a field.

Property Setter: field_order
Lesson. The code reads the current field order from the live meta, applies its moves, and writes the result back. That way a reordering someone else made in Customize Form survives, instead of being overwritten by a hard-coded list.
03

The Leads Activity DocType

The project's own record for a CRM touchpoint: a call, a meeting, a site visit, a registration, a tender.

What

A new DocType named CRM-ACT-.YYYY.-.##### with Type, Status, Date, Assigned To, a Link Type / Link pair, and an Attachments child table.

Where

New folder custom_crm_updates/doctype/leads_activity/, plus the child DocType Leads Activity Attachment.

Why

An activity is a record in its own right — it has its own status, owner, date and files, and it is created and listed independently. That is the signal that you need a DocType and not a field (or worse, a text area) on the Lead.

New DocTypeChild DocTypeDynamic Link
Lesson. The Dynamic Link pattern is worth memorising: a Select field holding a DocType name (link_type) plus a Link field whose options point at that Select (link_name). One record type can then attach to a Lead, a Prospect or an Opportunity without three separate fields.
04

Activities drive the Lead's qualification

Logging activities now moves the Lead through its qualification states by itself.

What

Creating a Registration activity sets the Lead to In Process. Any activity reaching Done marks the Lead Qualified and records Qualified By and Qualified On.

Where

LeadsActivity.on_update and set_lead_qualification in leads_activity.py.

Why

The status was being updated by hand and drifted from reality. The updates are written with db_set, not a full save(), for two deliberate reasons: the user logging an activity may not have write access to the Lead, and an unrelated Lead validation error (a duplicate email, say) must not block recording a phone call that really happened.

Hook: on_updatedb_setTimeline comment
Lesson. doc.db_set(...) writes one field and skips validation; doc.save() runs everything. Choose db_set for a small status nudge on a different document, and save() when the other document's own automations must run too. Every automatic change here also writes a timeline comment, so a user can always see why a status moved.
05

Create ▸ Activity (and no more Prospect)

The Lead's Create menu now offers Activity, pre-linked to that Lead.

What

"Prospect" removed from the Create menu, "Activity" added; the new activity opens with Link Type and Link already filled in. The Connections tab's + does the same.

Where

public/js/lead.js and the shared public/js/leads_activity_section.js, wired through doctype_js in hooks.py.

Why

A pre-linked record is one less chance to link an activity to the wrong Lead. The controller is subclassed (class LeadController extends erpnext.LeadController) rather than hooked with frappe.ui.form.on, because plain handlers run before ERPNext's own refresh — at which point the Create buttons do not exist yet and cannot be removed.

Client Scriptdoctype_jsController subclass
Lesson. Two ways to script a form: frappe.ui.form.on("Lead", {...}) for field reactions, and extending the app's controller class when you must act after the standard buttons are built. Ordering bugs in client scripts are almost always this distinction.
06

Activities shown as a real table the key pattern

The Lead's Activities tab lists its activities in a normal ERPNext grid — read-only, and kept in step automatically.

What

A section at the top of the Activities tab holding a child table of Leads Activity Detail rows: activity, type, date, status, assigned user, attachment count. Read-only, with a New Activity button instead of Add Row.

Where

Three Custom Fields on Lead, the child DocType Leads Activity Detail, sync_activity_table() in leads_activity.py, and the shared writer mirror_table.py.

Why

A child table has to store its rows inside the parent document — but the real records live in their own DocType. So the rows are a mirror: whenever an activity is created, edited, re-linked or deleted, the affected Lead's rows are rebuilt from the activities. The alternative, an HTML field rendering a list, was tried first and dropped: it cannot be filtered, sorted or exported, and users expect the grid's ⚙ column picker.

Custom Field: TableChild DocTypemirror_table.pyread_only · no_copy
Lesson. This "mirror table" is the most reusable idea in the project, and it is reused three more times (Opportunity activities, Project Tenders, Contacts). The technical reference explains exactly how it writes rows safely, why it compares before writing, and why it touches the parent's modified timestamp.
07

The Opportunity gets its own activities

The same table on the Opportunity — listing only the Opportunity's activities, never the Lead's.

What

An Opportunity Activities section identical to the Lead's. An Opportunity made from a Lead starts empty; the Lead does not show the Opportunity's activities either.

Where

The same three Custom Fields, now on Opportunity (overrides/opportunity.py), reusing activity_table_fields() and sync_activity_table().

Why

Pre-sales conversations and deal conversations are different histories and are reported on separately. Keeping them apart was a requirement, not an accident — and it foreshadows the contacts decision in Phase 2.

Reused helperTABLE_DOCTYPES
Lesson. When the second DocType needs the same feature, turn the field definitions into a function that returns them (activity_table_fields(label)) rather than copying the dicts. Adding a third DocType later is then one list entry.
08

Address & Contacts moved into its own tab

The Lead's address and contact blocks left the crowded Details tab.

What

A new Address & Contacts tab holding the address list, City/State/Country and the contact list. The tabs became: Details, Address & Contacts, Activities, Comments, Connections.

Where

One Tab Break Custom Field plus the field_order Property Setter from step 2; two more Property Setters blank the section's heading and stop it being collapsible.

Why

A Tab Break claims every field after it until the next tab, so the block had to be moved to just before Activities — otherwise Qualification and Additional Information would have been dragged into the new tab. Inside its own tab the section heading would just repeat the tab name, so it was emptied.

Tab Breakfield_order
Lesson. Tab and Section Breaks are ordinary fields in the order. Think of layout as one flat list with markers in it, not as nested containers — most layout surprises in Frappe come from forgetting that.
09

A Tendering activity type, and two new Opportunity statuses

New option values on one of our fields and one of ERPNext's.

What

Tendering added to Leads Activity → Type. Tendering and Won added to Opportunity → Status.

Where

Type: edited directly in leads_activity.json — our own DocType. Status: an options Property Setter on Opportunity, built in apply_opportunity_customizations().

Why

The new options are read from the original DocField row and our two appended, so re-running never duplicates them and any option a future ERPNext release adds is preserved. Hard-coding the full list would silently delete ERPNext's additions on the next upgrade.

DocType JSONProperty Setter: options
Lesson. Your DocType, your JSON. Someone else's DocType, a Property Setter — and build its value from what is already there rather than from a literal.
10

A Tendering activity creates a Project Tender

The first cross-app automation: saving an activity creates a record in another app.

What

Saving a Tendering activity on an Opportunity creates one Project Tender, named after the Opportunity, with its Client resolved to a real Customer, and moves the Opportunity to Tendering. One tender per activity — re-saving never creates a second.

Where

overrides/project_tender.py → create_project_tender_for_activity(), called from LeadsActivity.on_update. Two read-only Custom Fields are added to Project Tender: custom_opportunity and custom_leads_activity.

Why

Project Tender belongs to the contracting app, which is left untouched — so the link lives on our two Custom Fields. Those fields are also the idempotence mechanism: before creating, the code asks whether a tender already points at this activity. The tender is inserted with ignore_permissions=True because a Sales User has no role on Project Tender but must still be able to trigger the automation.

Cross-appignore_permissionsIdempotence by link
Lesson. Automations run again — on every re-save, on a background retry, on a bulk edit. Give each one a cheap question it can ask the database to find out whether it already ran. A link field pointing back at the trigger is the simplest such question.
11

The Opportunity's Project Tender tab

A third mirror table, this time of records owned by another app.

What

A tab between Items and Activities listing the Opportunity's tenders: tender, project name, client, status, total sell price.

Where

Two Custom Fields on Opportunity plus the child DocType Opportunity Project Tender; kept current by sync_opportunity_tenders(), triggered by a doc_events hook on Project Tender.

Why

Sales needed the tender status without opening the contracting module — and often without permission to. Reading it into a mirror table on the Opportunity sidesteps the permission problem entirely, because child rows belong to the Opportunity the user can already read.

doc_events on another app's DocTypeMirror table
Lesson. doc_events can hook a DocType from any installed app, and the hook simply never fires if that app is absent. That is why this whole feature degrades quietly on a site without contracting instead of crashing.
12

A Submitted tender marks its activity Done

The status relationship in the other direction — and the rule that was rewritten in Phase 2.

What

When a Project Tender's status becomes Submitted, the activity that created it is set to Done. Originally the Opportunity was also set to Won here — that half was removed in step 18.

Where

on_update and mark_activity_done() in overrides/project_tender.py.

Why

The guard doc.has_value_changed("status") makes it fire only on the save where the status actually changed, so re-saving a submitted tender does nothing. The activity gets a full save() here — not db_set — precisely so its own on_update runs and the Opportunity's activities table shows "Done" too.

has_value_changedfull save vs db_set
Lesson. has_value_changed(field) compares against the version loaded before this save. It is the standard way to answer "did this just happen?" and it is what keeps an idempotent automation from firing on every unrelated save.
13

Registration Done → the Lead becomes a Customer

Reusing ERPNext's own conversion instead of writing one.

What

A Registration activity reaching Done converts its Lead into a Customer, carrying the Lead's Customer Group and Territory. A Lead that already has a Customer is never converted twice.

Where

convert_lead_to_customer() and insert_customer() in overrides/lead.py, calling ERPNext's _make_customer.

Why

ERPNext's mapper is the same code behind the Lead's own Create ▸ Customer button: it copies the details, links the Lead's contacts and addresses to the new Customer and marks the Lead Converted. Re-implementing that would have drifted from core on the next upgrade. Only what the mapper leaves out is filled in.

get_mapped_docReuse core logic
Lesson. Before writing a conversion, search ERPNext for a @frappe.whitelist() function named make_* — most document-to-document conversions already exist. Call it and adjust the result.
14

Contacts shown as a table

ERPNext's contact list replaced by a grid on both Lead and Opportunity.

What

Core's contact_html list is hidden and a read-only Contacts table (Leads Contact Detail rows) shows contact, full name, email, mobile, designation and the primary flag, with a New Contact button.

Where

overrides/contact.py, two Custom Fields on each of Lead and Opportunity, one hidden Property Setter each, and doc_events on Contact.

Why

Same reasons as the activities table: filterable, sortable, exportable, familiar. Contacts attach to records through Dynamic Link rows inside the Contact, so this table is a mirror of those links — maintained from both ends, because a contact can change without its Lead being saved.

Property Setter: hiddendoc_events on ContactDynamic Link
Lesson. Hide core's version rather than deleting or disabling it. ERPNext still renders into the hidden field, nothing in its code breaks, and you can revert by removing one Property Setter.
15

Empty tables stay visible

A one-screen fix for a Frappe behaviour that hid the new buttons.

What

A read-only table with no rows no longer disappears, so its New Activity / New Contact button is always reachable — and the Project Tender tab, which contains nothing else, no longer vanishes.

Where

show_when_empty() in public/js/leads_activity_section.js, installed from each controller's setup.

Why

Frappe hides any read-only field that has no value. Each field control decides its own visibility in a method called get_status, so that method is wrapped for our tables only: when the original says "None" but the field is not deliberately hidden and the user can read it, the answer becomes "Read" — shown, still read-only.

Control wrappingget_status
Lesson. When a framework behaviour is in your way, find the smallest method that decides it and wrap that one method for your own fields — rather than forcing the field's hidden property on every refresh, which fights the framework on every render.
16

Customer Group and Territory made mandatory on the Lead

The conversion in step 13 needs them, so they are demanded up front — carefully.

What

A new Customer Group field beside Territory; both must be filled before a person can save a Lead, and the Customer created from it inherits both.

Where

One Custom Field, two mandatory_depends_on Property Setters, and the validate hook validate_customer_fields — overrides/lead.py.

Why

The obvious switch, reqd, is enforced on every insert — including the Leads ERPNext creates by itself from the website contact form, from an incoming email, or from an appointment, where there is nobody to ask. Those inserts would start failing. So the form is made mandatory with mandatory_depends_on: "eval:1", and a server check covers API and Data Import saves while letting ERPNext's own inserts through.

mandatory_depends_onHook: validate
Lesson. In Frappe v14, mandatory_depends_on is checked by the form only. If a rule must hold everywhere, it needs a server validate too — and think about who else creates this DocType before you make anything reqd.
17

Wiring it all together: hooks.py and the setup functions

How Frappe finds everything above, and how it is re-applied on any site.

What

doctype_js attaches the client scripts; doc_events registers the 12 Python handlers; after_migrate runs three setup functions (which create every Custom Field and Property Setter) and then three backfills (which fill the mirror tables for records that predate them); override_doctype_dashboards adds Leads Activity to the Connections tab.

Where

hooks.py, plus apply_*_customizations() in each override module.

Why

Every setup function is idempotent: create_custom_fields(..., update=True) creates or updates, make_property_setter replaces any existing setter for the same field and property, and the backfills skip records that are already correct. So bench migrate can be run any number of times, on any site, in any order.

hooks.pyafter_migrateIdempotent setup
Lesson. Think of after_migrate as "make the site match the code". Order matters — fields first, then the backfills that fill them — and every step must be safe to repeat, because it will run on every deployment forever.
Part 04 · Phase 2

The six modifications — steps 18 to 24

After the business used Phase 1, six rules were changed or added, plus two cross-cutting changes. 10 Oct 2026

Read first

These six are a good study of the second kind of customization work: not "add a feature" but "the rule we agreed was wrong". Notice how often the fix is to move a decision from the machine to the user — which is exactly what modifications 1 and 2 do together.

18

Modification 1 · Submitting a tender no longer wins the Opportunity

The automation from step 12 was cut in half.

What

A Project Tender becoming Submitted still sets its activity to Done, but the Opportunity is now left exactly as it is. The function that set it to Won was deleted.

Where

overrides/project_tender.py — mark_opportunity_won() removed; on_update() now calls only mark_activity_done().

Why

One Opportunity can have several Project Tenders, and submitting a tender is not winning the deal. The old rule marked the deal won the first time any price went out of the door, which inflated the won pipeline and made the Opportunity's status meaningless.

Removed automation
Lesson. Deleting an automation is a customization too, and it needs the same care: the test that asserted "Opportunity becomes Won" was rewritten to assert the opposite, so the old behaviour cannot come back unnoticed.
19

Modification 2 · Setting an Opportunity to Won asks which tender was approved

The decision removed in step 18 is now put to the user, at the moment they know the answer.

What

Choosing Won on the Opportunity opens a popup listing that Opportunity's Project Tenders — ID, project name, status, total sell price. The chosen one is stored in a new read-only Approved Project Tender field, and saving the Opportunity sets that tender to Won. The other tenders are untouched. Dismissing the popup puts the status back.

Where

Popup: public/js/opportunity.js. Server: get_opportunity_tenders() (whitelisted), validate_approved_tender() and apply_approved_tender() in overrides/project_tender.py. New Custom Field custom_approved_project_tender on Opportunity.

Why

Only a human knows which bid the client accepted. Two design choices are worth copying: the list is fetched from the server rather than read off the form, so it cannot be stale; and the tender is updated when the Opportunity is saved, not when the popup closes — writing from a dialog would change the document under the open form and the user's own save would then be rejected as out of date.

Client Script: dialogfrappe.whitelistHook: on_updateCustom Field
Lesson. A popup that changes data should normally record the answer on the form and let the ordinary save apply it. You get one transaction, one permission check, one audit trail, and no timestamp conflicts.
20

Modification 3 · A message confirms the new Project Tender

The smallest change in the batch, and the one users noticed most.

What

Saving a Tendering activity now shows a green message naming the new tender and linking to it.

Where

A frappe.msgprint at the end of create_project_tender_for_activity().

Why

The automation was invisible: the user saved an activity and nothing on screen suggested a tender had appeared in another module, so people created duplicates by hand. The message fires only on actual creation — a re-save returns before reaching it.

frappe.msgprintget_link_to_form
Lesson. Any automation that creates a record the user cannot see should say so, with a link. Use frappe.msgprint from the server — it reaches the user whether they saved from the form, and get_link_to_form builds the clickable link for you.
21

Modification 4 · A Registration activity requires an attachment

One rule, three layers — the clearest example in the project of how a Frappe rule should be built.

What

An activity of type Registration cannot be saved unless at least one file is attached. The Attachments table shows a red asterisk the moment the Type is set to Registration. A row with no file picked does not count.

Where

(1) mandatory_depends_on on the attachments field in leads_activity.json; (2) a validate handler in leads_activity.js; (3) LeadsActivity.validate_registration_attachment() in leads_activity.py.

Why

Registration is the activity that converts the Lead into a Customer (step 13), so the paperwork has to be on file. Each layer does something the others cannot: the asterisk tells the user before they try; the form handler gives a clear message instead of Frappe's generic "Missing Fields" dialog; the server check is the one that actually holds, for the REST API and Data Import too.

mandatory_depends_onClient validateServer validate
Lesson. The form's validate runs before Frappe's own mandatory check, so your message is the one the user reads. And reqd was not an option here because the rule depends on another field's value — that is precisely what mandatory_depends_on is for.
22

Modification 5 · A tender can only be Submitted once it is costed

A rule placed on another app's DocType without touching that app.

What

Setting a Project Tender to Submitted is refused unless all three cost tables — Direct Cost Details, Indirect Cost Details, Overhead / Deduction Details — have at least one row. The message names the empty ones.

Where

validate_submitted_rows() in overrides/project_tender.py, registered as a validate hook on Project Tender in hooks.py.

Why

Submitting means sending a price to a client, so an un-costed tender must not get there. The check lives in validate rather than in the status change alone, which means emptying a table on an already submitted tender is refused too. The contracting app's own controller was deliberately not edited — the rule is a CRM-side policy and belongs in the CRM app.

Hook: validateCross-app policy
Lesson. You can add validation to a DocType owned by another app from your own hooks.py. Prefer that to editing the other app whenever the rule is your business policy rather than that app's own integrity.
23

Modification 6 · The Opportunity's contacts are separated from the Lead's

Undoing something ERPNext does on purpose — in three places, because one was not enough. Refined in step 25.

What

The Opportunity's Contacts table now lists only contacts linked to the Opportunity — the Lead's contacts, including the ones that were on the Lead when the Opportunity was created, no longer appear there. Existing Opportunities are cleaned up on the next migrate. (At this point the Lead stopped showing the Opportunity's contacts too; step 25 put that half back.)

Where

(1) get_contact_rows() in overrides/contact.py no longer reads the party's contacts; (2) the grid's New Contact button in leads_activity_section.js now links the new contact to the record you pressed it on; (3) the Opportunity's Contact Person link query in opportunity.js now lists the Opportunity's own contacts.

Why

ERPNext deliberately merges an Opportunity's party contacts into its contact list, so the deal shows the Lead's people. The business wanted the two managed separately. Changing only the table would have been a trap: core leaves frappe.dynamic_link pointing at the party, so the New Contact button would have kept creating contacts on the Lead — invisible in the table the user just pressed the button in.

Mirror query changefrappe.dynamic_linkLink query filterBackfill cleanup
Lesson. When you change what a list shows, find everything that writes to it as well. A read and a write that disagree is the hardest class of customization bug to spot, because nothing errors — the record simply appears somewhere else.
24

Also in this batch · table ordering and Arabic messages

Two cross-cutting changes that touched every step above.

What

Ordering: every CRM mirror table now orders creation asc — oldest at the top, new rows appended at the bottom. The activities table previously sorted by the activity's own Date, and the contacts table previously floated the primary contact to the top. Messages: the errors and alerts of these automations are now written in Arabic, with field names, DocType names and status values left in English (Project Tender, Submitted, Registration, Attachments).

Where

Ordering: sync_activity_table(), tender_rows(), get_contact_rows(). Messages: the frappe.throw / msgprint calls in project_tender.py, leads_activity.py, and the dialog strings in opportunity.js / leads_activity.js.

Why

Ordering by creation rather than by a user-entered date is what makes "new rows at the bottom" actually true — a back-dated activity would otherwise jump to the top. The Arabic is written as the source string, inside _(), because every user on this bench has their language set to en: Frappe resolves _() against the user's language, so an ar.csv translation file would never have been shown to them.

order_by_() source strings
Lesson. Keep message text inside _() even when you write it in the target language — the string stays translatable, so a future site with Arabic or English users can override it with a translation file instead of a code change.
Part 05 · Phase 3

Follow-ups once it was in use — steps 25 and 26

Two changes requested after the six modifications had been used for a day. 11 Oct 2026

25

The Lead rolls up its Opportunities' contacts

Step 23 made the two tables strictly separate. Only half of that was wanted.

What

The rule is now asymmetric. An Opportunity still shows only the contacts linked to it. A Lead shows its own contacts and those of every Opportunity made from it — its own first, then each Opportunity's, oldest Opportunity first. "Linked Via" names the source of each row, and a contact linked to both is listed once.

Where

overrides/contact.py: a new contact_sources() decides where a table's rows come from; affected_docs() now also returns the Lead behind an Opportunity; a new refresh_party_lead() is hooked to Opportunity on_update and on_trash.

Why

A deal's contact list should be the people on that deal — but the Lead is the client record, and whoever opens it wants to see everyone involved, including the people added while chasing a particular Opportunity. Strict separation lost that overview.

contact_sourcesHook: Opportunity on_update / on_trashBackfill
Lesson. A roll-up needs a trigger the obvious event does not give you. Linking a contact to an Opportunity fires a Contact event, which is how the Lead finds out — but an Opportunity being created, re-pointed at another Lead or deleted changes the roll-up without any contact changing at all. Create ▸ Opportunity on the Customer

A one-screen addition that needed no new server code at all.

What

The Customer form's Create menu gains an Opportunity entry. Clicking it opens a new Opportunity already set to opportunity_from = Customer with this Customer as the party.

Where

New file public/js/customer.js, wired with one line in doctype_js.

Why

ERPNext already has the mapping — erpnext.selling.doctype.customer.customer.make_opportunity — and already registers it in frm.make_methods. But make_methods only powers the Connections tab's "+" button, so nothing put it in the Create menu where people look for it. Calling the same mapper means the Opportunity is built exactly as ERPNext builds it everywhere else.

Part 07

Deploying and verifying

What to run, in what order, and how to prove the result.

The four commands

bench --site <site> migrate            # creates/updates every Custom Field and Property Setter, then backfills
bench build --app custom_crm_updates   # bundles the client scripts in public/js
bench --site <site> clear-cache        # a DocType's own .js and its meta are cached per site
bench restart                          # Python changes need the workers restarted
  • Per site. Each site has its own database, so migrate and clear-cache must be run for each one (site1.local and friendmix.local here).
  • Order matters. migrate before build is not required, but clear-cache must come after both, or the browser keeps the old form script.
  • Safe to repeat. Every after_migrate step is idempotent, so re-running migrate never duplicates a field or a setter.

Proving it works

The app ships 90 automated tests across two files. They create their own Leads, Opportunities, activities and tenders and roll everything back afterwards.

bench --site <test-site> run-tests --app custom_crm_updates
Honest note

89 of the 90 pass. One test, test_mandatory_when_saved_by_a_user, fails on this bench and failed before any of this phase's work — ERPNext's test setup writes user defaults for Customer Group and Territory, and Frappe fills empty fields from them, so the mandatory error never fires inside the test runner. The rule itself works outside the runner. Run tests on a dedicated test site: on a live site, ERPNext's sample records are saved permanently.

Part 08

Doing this yourself

The seven habits this project would hand to someone starting their first ERPNext customization.

Habits worth copying

  1. Make a separate app. bench new-app once, and never edit ERPNext.
  2. Create fields in code, not by clicking — then every site is one migrate away from identical.
  3. Make every setup function idempotent, because it runs on every deployment.
  4. Put rules on the server, convenience on the client — and when the rule matters, do both.
  5. Ask "did this just happen?" with has_value_changed, and "did I already do this?" with a link back to the trigger.
  6. Say so when you create something invisible — msgprint plus a timeline comment.
  7. Write the test that pins the rule down, especially when you remove a rule.

Mistakes this project hit (so you can skip them)

  • Hiding a field and forgetting to clear it — step 1.
  • Expecting insert_after to move a core field — step 2.
  • Using reqd where ERPNext also creates the record itself — step 16.
  • Hooking a form with frappe.ui.form.on when the code must run after core's buttons — step 5.
  • Changing what a table shows without changing what writes to it — step 23.
  • Aggregating across a link without handling the link itself moving — step 25.
  • Writing a mapper that ERPNext already ships — step 26.
  • Letting an automation decide something only a human knows — steps 18 and 19.
  • Writing from a dialog straight to the database while the form is open — step 19.
